# Durable records and candidate identity

Use the project's existing paths and formats. A tiny task can keep one compact **immutable baseline** and one **mutable evidence** record. Never mix later review or acceptance results into a frozen requirement file: requirements affect candidate identity, while evidence-only records do not. Every record has an owner, revision or time, and a stable path that a fresh role can read. Board posts link to records; their 200-character text is not the source of truth.

## Minimum fields

| Record | Owner and fields |
|---|---|
| Request | PM: original user text or stable reference; repository/branch; constraints; approvals already given; requested outcome; open decisions. Preserve the original even when scope changes. |
| Product baseline | Product manager: revision `product-rN`; problem/users; priority; stable `PR-n` IDs and observable criteria; explicit versus inferred scope; user-facing performance threshold value or `none required` with reason; dated competitor sources/findings, `not applicable` with reason and PM acknowledgment, or `not performed` with tool/network blocker; exclusions and user decisions. PM checks first revision against request before EL work depends on it. Each later revision preserves prior text or diff, reason, and approver (user via PM for a scope change); never reuse a PR ID. |
| Engineering brief | EL: revision; architecture/interfaces; `ER-n → PR-n` map; final tier and staffing rationale; task IDs/owners/file boundaries; dependency and integration order; test plan; technical performance threshold value or `none required` with reason and owner; recovery/rollback for data, interface or operational impact. Each later revision preserves prior text or diff, reason, and approver; never reuse an ER ID. |
| Task and review | EL/engineer/reviewer: task/PR/ER IDs; base and immutable diff or commit; author; PM-assigned reviewer, host/model; commands/results; finding ID/severity/evidence; fix or authorized disposition; reviewer recheck; affected-file/requirement assessment. |
| QA | QA: candidate ID and product revision; applicability of acceptance, integration, end-to-end, performance; authored tests and their independent review; environment/command/result; threshold and owner; defects, reruns, omissions with EL concurrence. |
| Product/EL acceptance | Each accepting role: candidate ID and product revision; per-PR or per-ER result, observed method/evidence, rejected item or limitation. Product records direct exercise for each user-visible criterion or PM's reason for relying on named QA evidence. |
| PM status/final report | Task states (`ready`, `active`, `review`, `QA`, `blocked`, `accepted`), dependencies, next check, changed estimate, risks and user questions; final PR-to-task-to-QA-to-product trace, ER-to-implementation-to-review trace, delivered scope, checks, omitted research/tests, accepted findings, inferences not user-approved, pending decisions. |

An agent's durable brief names the request, requirement revision, task IDs, owned paths, expected deliverable, checks, and return path. On **both hosts**, each role's first board post is `BRIEF: <path> tasks: <IDs>`; on Codex this also lets a supervisor replacement recover details unavailable from the encrypted spawn message. An agent needing PM action both posts and returns `{action, task_id, artifact_path, blocker}`. A replacement re-reads this brief, current artifacts, and last committed state before work.

## Freeze and compare a candidate

Each task review binds to an immutable diff or commit against a named base and the linked requirement revision. Concurrent writers use separate branches/worktrees where supported; otherwise serialize shared-file edits. EL integrates reviewed tasks and freezes the source **before final QA, product, and technical signoffs**. It records the project root, deliverable root(s), exact evidence-only and generated-output exclusions, and resulting path list. Prefer the whole project root so a new source directory is visible. Enumerate regular files under those roots whether Git-tracked or untracked; include **all** operative code, tests, skill Markdown, configuration, and requirement baseline files. Exclude VCS metadata such as `.git/`; declare evidence-only directory prefixes before freeze so later evidence files under them remain excluded, and never place operative code, tests, configuration, skill instructions, or requirements in those prefixes. If a deliverable is a symlink or has a path that cannot be represented as UTF-8, stop and choose a documented portable representation before signoff; never silently omit it.

The manifest byte format is exact. Normalize each file path to a project-relative POSIX path with `/` separators, no leading `./` or absolute prefix, and UTF-8 encoding. For each regular file, compute SHA-256 of its raw bytes and lowercase the full 64-character hexadecimal digest. Sort entries by unsigned byte order of their UTF-8 path bytes, independent of locale. Serialize each entry as `path_utf8 + NUL + file_hash_ascii + LF` with no header; concatenate in that order. `candidate=<id>` is the full lowercase hexadecimal SHA-256 digest of those concatenated manifest bytes. Record the manifest bytes and inclusion/exclusion rules in an evidence file outside the deliverable set, and Git commit IDs separately as provenance. This rule also works without Git. At **every** freshness comparison, PM re-enumerates roots using the recorded rules, including untracked files; compares the newly derived path set with the frozen list; and recomputes hashes and the candidate ID. An added or deleted deliverable must change or invalidate the candidate. Do not merely rehash the frozen list.

Keep mutable review, test-result, traceability-result, acceptance, status, and evaluation files outside the deliverable list. If a compact record contains both requirements and results, split it before freeze. Writing evidence alone must leave the candidate ID stable. Every excluded path has an explicit evidence or generated-output reason; a new excluded path requires EL and reviewer confirmation that it contains no operative requirement, source, configuration, test, or skill instruction.

EL and reviewer jointly decide whether a post-review task edit intersects a reviewed file or linked PR/ER. Reopen that task review when it does. Any change to the integrated deliverable path set, content manifest, or product revision reopens **all** final QA, product, EL, and judge signoffs; run affected checks against the new frozen candidate. Evidence-only record edits do not reopen them. PM compares current path set, manifest ID, and requirement revision to every acceptance result and the judge's `candidate=<id> req=<revision>` reason before `swarm deactivate`. Swarm checks only the latest `met` verdict; it does not detect stale evidence.

If a writer stops unexpectedly, PM confirms the old writer is fenced by a supported host stop or supervisor action before transferring a shared claim. A stale board status is insufficient. If fencing cannot be confirmed, keep shared files blocked or use an independent workspace; uncommitted partial edits are unreviewed input. On board outage, reconcile queued posts and ownership before accepting or reassigning shared work.
