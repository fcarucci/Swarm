# Engineering team product baseline

**Owner:** product manager (Eddie)
**Requirement revision:** `product-r1`
**Status:** proposed for PM comparison with the original request; acceptance results belong in a separate evidence record.
**Sources:** [approved design](../../specs/2026-09-29-engineering-team-design.md), [approved implementation plan](../../plans/2026-09-29-engineering-team.md), and [original-request map U1–U7](../../reviews/2026-09-29-engineering-team/initial-product-roles.md).

## Problem and outcome

A software request should move through product definition, technical planning, implementation, independent review, QA, and acceptance using the existing Swarm job and board on Claude Code or Codex. The invoking agent manages the job as project manager (PM). Team size follows task complexity and actual host capacity. A user should receive a report that distinguishes delivered behavior, evidence, limitations, and any decision still needed.

This baseline describes the **skill to build**, not a claim that either host has passed a behavioral evaluation. The original request's U1–U7 duties are explicit below. Workflow details are derived from the reviewed design and plan; they do not add a user signoff gate to the already approved implementation.

## Scope, decisions, and research

- **In scope:** `swarm:engineering-team` Markdown skill and references, README entry, role and artifact contracts, Claude/Codex host instructions, and independent behavioral evaluation evidence described in the approved plan.
- **No goals:** new Swarm runtime enforcement, board schema, autonomous scheduler, plugin installation or release, deployment/publication of a user project, fixed four-member team, guaranteed blind review, or automatic authority for product/QA/EL custom role labels.
- **Existing authorization:** the approved plan authorizes creating and reviewing this skill. User decisions remain necessary for consequential scope changes or for leaving high/critical findings unfixed; routine inferred details do not require blanket approval.
- **External competitor research for this implementation:** **not applicable**. This is an internal orchestration skill with an approved architecture and defined Swarm interfaces. A market comparison would not decide its requirements. PM acknowledgment is required by the design and is recorded outside this frozen baseline. The *skill's future product manager* still has a research duty where research can inform a user-facing product decision; inaccessible tools must be reported as a blocker, not described as irrelevance. No competitor findings are claimed here.
- **Consequential inferences:** the tier rules, SHA-256 candidate manifest, independent host dry runs, installed custom-role capability floor, and candidate-bound signoffs come from the reviewed design/plan rather than the short user request. They are marked `design-derived` in the table. No original request item is excluded or deferred.

## Product acceptance method

At candidate freeze, the accepting product manager reads this revision, the original U1–U7 map, the actual skill and references, and the host evaluation record. They record a result for **each PR ID** against the same candidate manifest and revision. They directly exercise the user-visible workflow where feasible, identify the method and observed result, and distinguish static document coverage from observed host behavior. Any reliance on QA evidence needs the PM's recorded reason. `Pending` host runs, unsupported installed runtime, missing independent review, or unmet criteria remain open; a green static validation does not turn them into acceptance.

The PM compares this baseline to the original request before EL planning. A later requirement change gets a new revision with the earlier text or diff and its approver preserved. Acceptance results, review findings, status, and evaluation observations are stored separately so writing evidence does not mutate this requirement baseline.
