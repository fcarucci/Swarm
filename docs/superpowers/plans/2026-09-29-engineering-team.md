# Engineering Team Skill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Swarm plugin skill that assembles and runs a project manager, product manager, engineering lead, engineers, and QA through specification, implementation, independent review, and acceptance in Claude Code and Codex.

**Architecture:** The skill is an orchestration layer over the existing Swarm job, board, custom-role labels, judge, and verifier mechanisms. Its entrypoint stays short; references define role handoffs, artifacts, host-specific spawning, and recovery. The invoking agent acts as project manager (PM). The engineering lead (EL) decides technical staffing and task ownership; PM launches bounded root-level agent invocations against a declared or conservative slot budget. The first version adds no runtime role enforcement or schema changes.

**Tech Stack:** Markdown skills in `skills/`, Swarm CLI and board, Claude Code `Agent` and Codex `spawn_agent`, Python `unittest` for existing runtime coverage, skill validator for metadata.

**Spec:** `docs/superpowers/specs/2026-09-29-engineering-team-design.md`

**Status:** Reviewed plan; both independent Claude reviewers returned READY after revision. See the [review resolution](../reviews/2026-09-29-engineering-team/resolution.md) for findings and final corrections. Skill implementation and host behavioral evaluations remain future work.

## Global Constraints

- Support both Claude Code and Codex; record a known host slot limit from current session context/config or use conservative serial scheduling when unknown. Never probe capacity with a member spawn. The default `max_per_job = 4` is a nonrefundable member-child budget, not total team size; root PM spawns are its default path.
- Roles are workflow instructions and board metadata. Only built-in `judge` and `verifier` have special enforcement; a custom `reviewer` is a normal worker.
- Claude routes by `[swarm job: <job>]` and `[swarm role: <role>]` in the agent prompt. Codex joins the session job and reads role from `task_name="<role>__<task>"`; it cannot read prompt tags in its encrypted child message.
- A swarm member spawning a short helper must stay within `max_per_agent`, `max_per_job`, and `max_depth`; on Claude it needs job and spawn-justification tags. Counts are not refunded when a child exits or a host rejects a launch. Roles are launched at root by PM in bounded invocations that return control; PM counts active invocations against the declared or conservative budget and treats a returned agent as occupying its slot until the host shows it released.
- PM owns job activation, board polling, scheduling, and user reports. The main session receives no member hook injection: PM explicitly joins/reads or monitors the board and receives a direct return from each bounded role invocation. An optional PM delegate has only bounded reporting/planning work.
- The user retains authority over requested scope. PM can carry forward reasonable inferences and ask only for material choices that cannot be inferred; the product manager cannot redefine the request by signing off its own revision.
- Every delivered change, including QA-written test code, gets a reviewer who did not author it. PM assigns reviewers; author-selected or self-review does not pass. Product, technical, and QA acceptance are separate decisions on an identified candidate and requirement revision.
- Complexity changes role allocation and review depth, not the independence rule: tiny work uses three distinct contexts (invoker combines PM/product/EL, one engineer implements, another reviewer performs independent review and appropriate QA); moderate and complex work use distinct roles as specified in the design.
- QA writes missing relevant tests, runs applicable acceptance/integration/end-to-end/performance checks, and records omissions with EL concurrence. Product sets user-facing performance thresholds and EL sets technical ones before measurement.
- A small change may use one compact planning artifact; before freeze, separate immutable baseline content from mutable evidence records so evidence never edits a hashed requirement file. Product manager addresses competitor research when relevant; `not applicable` and `blocked by unavailable research access` are distinct, both visible to PM and user.
- Independent role launches, especially reviewer, QA, product acceptance, verifier, and judge, get a fresh task context. In Codex specify `fork_turns: "none"`; a follow-up keeps the old role and context and cannot convert an author into an independent checker. Board history remains visible, so do not promise blind review.
- The source capability floor is custom-role support from commit `634aece`; plugin version `0.1.0` alone is ambiguous. Preflight installed behavior via role enrolment on each host and record installed source/version. Do not silently install or release a plugin.
- No external publication, merge, deployment, or other consequential mutation is implied by this skill; use the user's authorization and the host's normal gates.

## Review Focus

1. No declared host cap or an exhausted slot: PM queues work, uses an actual released slot or a same-role follow-up, and does not consume a member spawn as a capacity probe. Task 2 evaluation.
2. Author assigned as reviewer, or QA tests lacking review: PM assigns a distinct agent and blocks acceptance until independent review. Task 1 contract; Task 3 run.
3. Code or PR revision after judge `met`: PM detects candidate/revision mismatch, reopens affected evidence and obtains a new verdict before completion; the Swarm gate itself does not detect staleness. Task 1 contract; Task 3 run.
4. Agent with partial edits stops: PM confirms host stop before reassignment, transfers claim, and replacement reconstructs from durable brief and reviews partial state. Task 2 contract; Task 3 run.
5. Research inaccessible, performance threshold absent, or evidence-only metadata changed: report the relevant limitation or exclusion without inventing research, a passing measurement, or a recursively stale candidate. Task 1 contract; Task 3 run.

## Task 1: Role and Evidence Contract

**Files:** Create `skills/engineering-team/SKILL.md`, `skills/engineering-team/references/team-roles.md`, and `skills/engineering-team/references/artifacts.md`.

**Interfaces:** Consumes the design spec, original U1–U7 request, and existing Swarm role semantics. Produces a concise entrypoint and role/artifact contracts used by Task 2.

- [ ] **Step 1: Define the entrypoint.** Add YAML `name: engineering-team` and a description specific to multi-role software delivery with Swarm. State the PM invocation, product baseline, EL plan/staffing, implementation, independent review, QA, three acceptance decisions, and judge gate. Link references progressively, without copying the full playbook into the entrypoint.
- [ ] **Step 2: Write the role contract.** PM cross-checks the product baseline against the original request and records each inference; only material scope choices the team cannot infer go to the user. Product manager can escalate ambiguity through PM and independently checks user-visible behavior, recording direct observation or reliance on QA evidence per criterion. EL determines complexity, task ownership, architecture, software requirements, staffing and technical acceptance. Engineers implement, acknowledge review findings, fix them, and return them to the reviewer. QA writes missing applicable tests, executes them, and signs QA evidence; every QA code change receives independent engineering review. Define compact tiny-role combination and distinct moderate/complex roles from the design, while preserving author/reviewer and author/product-acceptor separation.
- [ ] **Step 3: Define finding and escalation authority.** PM chooses the independent reviewer; author never chooses or signs off its own work. Reviewer confirms a fix. EL and reviewer may disposition low/medium findings with reasons; unfixed high/critical findings and PR exclusion/deferral require a user scope/risk decision via PM. Technical disputes go to EL, product-fit disputes to product manager, and scope disputes to user. A judge `not_met` returns to PM for owner assignment and rechecks. Every delivered change receives review; depth follows EL's recorded risk class, not a vague `material` escape.
- [ ] **Step 4: Define artifact fields and identity.** Preserve request and approval history; version PR IDs/criteria and ER-to-PR map. Record competitor findings with source/date, or distinguish `not applicable` from `blocked by inaccessible sources`, with PM acknowledgment for user-facing research omission. Include staffing request, task ownership, dependency schedule, QA applicability/omission with EL concurrence, predeclared performance threshold owner/value, review findings and disposition, product direct observations, and status report. For task review, identify an immutable diff or commit against a named base plus requirement revision. For integrated QA/product/EL/judge decisions, freeze a SHA-256 manifest ID computed from sorted relative paths and hashes of all deliverable code, tests, skill Markdown, configuration, and requirements; record a Git commit as provenance only. EL records the frozen deliverable path list, including requirement baselines; additions/deletions update that list. Keep all mutable review/test-result/traceability-result/acceptance/status/evaluation files outside it. Split a compact artifact containing both baseline and results before freeze; never exclude code, test code, operative requirements, or skill instructions as evidence. A changed task diff invalidates its affected review; a changed integrated deliverable or traced PR invalidates affected downstream QA and acceptance. PM compares current manifest ID/revision to each signoff and judge reason before completion.
- [ ] **Step 5: Check static contract and commit.** Read the new files against design and original U1–U7; mark every request item as covered or unresolved. Validate frontmatter name/description, reference links, and `git diff --check` with host-portable checks; if the Codex skill validator is accessible, run it too. Commit the Task 1 docs as a draft. This proves document structure and coverage, not host behavior.

## Task 2: Host Orchestration and Recovery

**Files:** Create `skills/engineering-team/references/hosts.md`; modify `skills/engineering-team/SKILL.md` to link it and `README.md` to expose the skill.

**Interfaces:** Consumes Task 1 role/artifact contracts and current Swarm CLI/host conventions. Produces executable setup, bounded invocation, capacity, recovery, and completion procedures.

- [ ] **Step 1: Document capability preflight.** Check that installed source includes custom roles introduced by commit `634aece`; `0.1.0` alone does not prove this. Check `swarm doctor`, the active board/backend, and a first safe role invocation that makes a tool call and posts `BRIEF:`, followed by `swarm status --job <job> --all-agents` showing that agent with its role, even if already returned. Checking before that tool call or using active-only `who` can give a false failure. If it shows an agent type instead, stop the team run and report an unsupported installed runtime; do not auto-install or silently claim custom roles worked. Record each host's source identity and available network/research tools. Codex Swarm sandbox may have no network; report blocked research separately from irrelevance.
- [ ] **Step 2: Give exact host launch and PM board procedures.** Claude: `swarm activate --job ... --goal ...` and role/job tags in every prompt; Codex: one session job, `task_name` examples for `project_manager`, `product_manager`, `engineering_lead`, `engineer`, `reviewer`, `qa`, `verifier`, and `judge`. Mark `verifier` and `judge` as built-in, and custom roles as metadata. Codex uses `fork_turns: "none"` on fresh independent spawns and verifies support during dry run. PM runs `swarm join --job J --key orchestrator`, then `swarm read --job J --key orchestrator` at turn start and before waves because the main session gets no member hook messages. Every bounded role invocation posts `BRIEF: <durable path> tasks: <IDs>` first and returns a structured action request with requested action, task ID, artifact path, and blocker directly to PM; no staffing request waits indefinitely for an unread board message. Review briefs contain requirements, diff, and checks; reviewers inspect those sources independently before treating any author narrative visible on the shared board as proof.
- [ ] **Step 3: Specify scheduling and recovery.** PM reads a known limit from the session/config; when unknown, schedules conservatively in serial waves. EL decides technical staffing and assignments; PM launches roles at root, returns infeasible staffing requests to EL, tracks queued work, records whether the budget includes the root, and treats returned agents as still occupying slots until host evidence shows release. Bounded implement/review/fix/test/accept invocations return control, then PM verifies the host lifecycle and slot state before the next wave; Swarm `stop_quiet_minutes` is not a host slot signal. Root failures signal capacity; member spawn probes are forbidden because caps are nonrefundable. Reuse a Codex agent only for the same role; an implementation or test author cannot use follow-up to become the independent checker of that change, while the product manager still owns product acceptance and EL still owns technical acceptance. Do not invent a host close tool. If a required fresh checker cannot be launched and no supported lifecycle action can release capacity, report the blocker and needed fresh-session or authorized-host route; do not retry without a changed capacity signal or weaken independence. For manual reassignment, confirm old agent stopped via supported host status/tool or wait for observed stop, then transfer ownership and review partial edits. Replacement reconstructs from brief/artifacts, never from task name alone. On board outage defer shared claims, gated spawns, and acceptance. Call `swarm wait` whenever PM ends a turn with work remaining and no agent active; resume on return.
- [ ] **Step 4: Specify completion and documentation.** Use built-in judge only when a goal is activated; its `met` reason carries `candidate=<id> req=<revision>`. PM compares current integrated identity/revision to the latest verdict and acceptance records before `deactivate`; the board gate checks only the latest `met`, not staleness. Reopen changed evidence and request new approval/verdict when mismatched. A verifier's `VERIFIED` count also does not bind to a candidate. Add README entry and a sequence that includes a final product/EL/QA acceptance wave, whether each role resumes same-role or launches fresh from artifacts.
- [ ] **Step 5: Validate and commit.** Check YAML frontmatter name/description, all relative reference links, Claude/Codex command syntax against `skills/swarm/SKILL.md`, and `git diff --check`. Run the Codex quick validator only where it is available; on Claude use equivalent frontmatter/link checks. Commit docs as draft. No Markdown keyword assertion counts as behavior evidence.

## Task 3: Independent Behavioral Evaluation

**Files:** Create `docs/superpowers/evaluations/2026-09-29-engineering-team.md`; modify Task 1–2 skill files only for observed defects.

**Interfaces:** Consumes the frozen draft skill and both-host fixtures. Produces preregistered pass/fail criteria, raw observation links, grader decisions, and explicit pending results.

- [ ] **Step 1: Preregister fixtures before any run.** Write U1–U7 trace to skill clauses and expected host observations. For each scenario record the user fixture, seeded repository state, injection, expected owner/board post/gate, and a failing negative control; commit expectations before execution. Include positive and deliberately failing cases so a grader that accepts everything is exposed. Paper walkthroughs may catch design ambiguity but are not behavioral evidence.
- [ ] **Step 2: Run fresh independent agents.** A fresh executor on each host receives the skill and user fixture, with no solution or plan. Separate grader agents inspect resulting board messages, artifacts, candidate identity, role roster, and final decision against preregistered expectations. Preserve transcripts or stable evidence references and explicit pass/fail per scenario; the skill author cannot grade its own output.
- [ ] **Step 3: Exercise core reroutes.** Seed an engineer defect that a different peer reviewer must find, an integration failure QA must reject and retest after repair, and a product criterion the first candidate misses that product manager must reject before later acceptance. Include QA-authored test review, research inaccessible versus genuinely irrelevant, and a missing performance threshold. Inject a proposed review assignment naming the implementation author; pass only when PM rejects that assignment and obtains a distinct reviewer, not when Swarm is claimed to enforce it. Check PM receives/acts on the EL staffing request through direct return plus board polling.
- [ ] **Step 4: Exercise capacity, failure, and staleness.** Use a throwaway `SWARM_CONFIG` with `max_per_agent = 1` and `max_per_job = 1` to verify member-child refusal and PM requeue/root scheduling. Induce host slot exhaustion only if the host exposes a safe reproducible limit; otherwise mark that scenario pending and retain the conservative-serial policy. Stop an engineer mid-edit with a verified supported host mechanism, confirm stop before replacement, and inspect replacement reconstruction from the durable brief. Change a PR and candidate after a `met` verdict, then confirm PM refuses completion until affected product/EL/QA checks and a new matching verdict; an evidence-only metadata edit must not reopen them. Seed a compact baseline mixed with results and require separation before freeze; changing an actual requirement afterward must change its bound identity and reopen gates. On Codex, verify fresh independent forks in observed spawn metadata and that PM rejects wrong-role follow-up in its workflow; Swarm itself does not block that follow-up.
- [ ] **Step 5: Decide readiness.** Both Claude and Codex must show role enrolment on an installed runtime with the source capability floor and pass the core scenario suite before claiming both-host behavior. A missing host run is pending, not passing; a draft may be committed with that status. If a runtime defect appears, record reproduction and open a separately scoped regression/fix task; do not claim the docs fixed runtime behavior. Correct observed skill defects, rerun only affected scenarios plus one representative successful flow, and record the new evidence.
