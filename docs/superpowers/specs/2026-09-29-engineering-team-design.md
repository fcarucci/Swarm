# Engineering Team Skill Design

**Status:** Reviewed plan; both independent Claude reviewers returned READY after revision. See the [review resolution](../reviews/2026-09-29-engineering-team/resolution.md) for findings and final corrections. Skill implementation and host behavioral evaluations remain future work.

## Purpose and boundary

Add a `swarm:engineering-team` skill that turns a user request into a planned, implemented, reviewed, tested, and accepted software change. It must work in Claude Code and Codex through the existing Swarm board. The skill supplies role briefs, decisions, artifacts, and gates; the existing `swarm:swarm` skill supplies coordination, role labels, spawn limits, verifier restrictions, and the judge's job completion gate.

The team size follows the work and available host slots. Four is a possible session limit, not a team template. A small task can use one engineer and one independent reviewer in sequence. Work needing several independent components can use more engineers when slots permit. The project manager schedules bounded role invocations in waves so review, QA, and acceptance still happen when roles cannot run at once.

The invoking agent is the **project manager (PM)** and owns the active Swarm job, scheduling, board status, and user reports. The PM joins the board with an orchestrator key, reads it on wakeup and before every staffing wave, and replies to directed requests. A subagent needing PM action both posts to the board and returns a structured request (requested action, task ID, artifact path, blocker) to its parent; it does not wait indefinitely for an unobserved board post. The PM may delegate a bounded planning or reporting task to a `project_manager` custom role, but that delegate cannot own job activation, host-only spawns, or final user communication unless the host actually permits those operations. The **engineering lead (EL)** decides technical staffing, work partitioning, and engineering task ownership. The PM root-spawns the requested roles by default, preserving EL assignments and reporting capacity constraints back to the EL. Nested spawns are only for bounded helpers needed synchronously, within nonrefundable per-agent, per-job, and depth caps.

The user remains the authority for requested scope and any acceptance decision that requires changing it. Product manager acceptance means the candidate meets the current user-approved or reasonably inferred requirements; it does not authorize the product manager to redefine the request. The PM independently checks the first product baseline against the original request before EL planning, including every inference and exclusion. A product manager can flag a blocking ambiguity that the PM must route to the user. The team proceeds on unaffected work. A new user decision is needed only for a consequential ambiguity or scope change unavailable from existing authorization; there is no blanket approval gate for every moderate task.

## Staffing tiers and independence

| Tier | Trigger and staffing authority | Role allocation | Required separation |
|---|---|---|---|
| Tiny | One bounded change, one component, low integration risk; PM's intake size is provisional until EL assessment | Three distinct contexts: PM combines PM, product, and EL duties in one compact brief; one engineer implements; a separate reviewer performs independent review and appropriate QA checks | Author cannot review its own code or tests or give product acceptance; reviewer sees final diff and evidence |
| Moderate | User-visible behavior, nontrivial integration, or multiple requirements; EL confirms the tier and engineer count | Distinct product manager, EL, engineer pool, independent reviewer, and QA, scheduled in waves when needed | Author/reviewer, author/QA, and author/product acceptance stay separate |
| Complex | Multiple components or work streams, sensitive data/security, migrations, public interfaces, or difficult recovery; EL can upgrade the tier during discovery | Distinct roles as above; EL adds engineers, reviewer coverage, and QA coverage for each independent stream based on dependencies and risk | Every delivered code change, including QA test code, gets an independent reviewer; final integrated candidate has cross-component review |

The EL records the final size, engineer assignments, review depth, and any upgrade in the engineering brief. A tiny task can stay small even when the review is independent. A moderate or complex task can run roles sequentially when slots are scarce. Same-model reviewers are valid; cross-host review is optional when both hosts are available. Independence requires a different person or agent context from the author, not a different model. The PM assigns reviewers, never the author. Shared Swarm messages and optional memory may expose author context, so the skill cannot promise a blind review; a reviewer must inspect the change and requirements directly rather than accept the author's account.

## Role contract

| Role | Owns | Must receive | Must produce | Acceptance authority |
|---|---|---|---|---|
| PM (invoking agent; optional `project_manager` delegate) | Schedule, dependency tracking, slot allocation, risks, status reports, decision log, user questions | User request and all role outputs | Job brief, staffing schedule, progress reports, final delivery report | Confirms process gates and reports outcome; cannot waive product or technical acceptance silently |
| Product manager (`product_manager`) | Problem statement, user outcomes, competitor research, scope, product requirements | User request, constraints, available product evidence | Product brief, prioritized requirements, acceptance criteria, research result or reason it was unavailable, and assumptions | Assesses delivered behavior against product criteria; may require PM to escalate blocking ambiguity |
| EL (`engineering_lead`) | Architecture, engineering requirements, interfaces, implementation plan, engineer count and task boundaries | Current product baseline, repository constraints | Architecture/technical brief, task plan, staffing request, integration review | Accepts implementation against technical and product traceability; cannot replace product acceptance |
| Engineers (`engineer`) | Assigned implementation, focused tests, integration, fixes | Assigned tasks and requirements | Code, test evidence, handoff notes, responses to reviews | Own work cannot be its own independent review |
| Peer reviewers (`engineer` or `reviewer`) | Independent review of another agent's delivered code or tests | Requirement IDs, diff, tests, architecture | Findings with severity, evidence, resolution verification | Approves reviewed task only after findings are fixed or dispositioned by the authorized person |
| QA (`qa`) | Writing, extending, and executing relevant acceptance, end-to-end, integration, and performance tests | Requirements, architecture, built candidate, environments | Test plan and test code, execution evidence, defects, retest results, justified omissions | Signs off test evidence and remaining quality risks; does not decide product fit alone |
| Verifier (`verifier`, optional) | Independent checks of `DONE` claims | Claim and reproducible evidence | `VERIFIED` or `FAILED` board reply | Validates specific claims, not overall product acceptance |
| Judge (`judge`, recommended for moderate and complex jobs) | Job goal decision | Requirements, evidence, product/EL/QA results | `met` or `not_met` verdict with reason | Controls the existing Swarm completion gate when `--goal` is used |

Custom role labels grant ordinary worker permissions only. PM, product, EL, engineer, reviewer, and QA powers in this table are **prompt and workflow conventions**. Only existing Swarm controls enforce the judge seat and verdict, verifier write/spawn restrictions, per-agent/per-job spawn caps, maximum depth, and some host routing. The skill must not present peer review, quality approval, or product signoff as code-enforced when they are evidence and PM checks.

## Artifacts and traceability

Keep artifacts in the project's existing conventions and version control when they are useful to the project. For a small change, one concise planning artifact can contain multiple sections. At candidate freeze, keep the requirement/engineering baseline immutable and put mutable review, test, traceability-result, acceptance, status, and evaluation records in a separate evidence file. Compact mode may use one frozen baseline and one evidence file; it must not mix mutable signoffs into hashed baseline files. Each artifact names an owner and its current revision. The artifacts must be sufficient for a fresh role invocation to continue without a prior agent's private context.

1. **Request record:** original user request, constraints, repository and branch, definition of done, and approvals already given. PM owns it. It is never silently rewritten.
2. **Product brief:** problem, target users, goals, non-goals, assumptions, competitor findings with dated sources when research informs the decision, prioritized requirement IDs (`PR-1`, etc.), observable acceptance criteria, and baseline revision. Product manager owns it; PM checks it against the original request before EL planning. Each consequential inference is marked. Record `not applicable` with a reason and PM acknowledgment when research adds no value, or `not performed` with the actual tool/network blocker when research is relevant but unavailable. Do not invent findings. Preflight available research tools instead of assuming a host's network status from the plugin default. Report either omission to the user.
3. **Engineering brief and work plan:** architecture, dependencies, interfaces, constraints, technical requirement IDs (`ER-1`, etc.) linked to PR IDs, task owners, integration order, verification commands, rollback/recovery notes for changes with data, operational, or interface impact, and requested engineer count. EL owns it.
4. **Traceability record:** each PR maps to an implementing task, QA check, and product acceptance result; each ER maps to implementation and technical review. Exclusion or deferral is explicit and requires a user decision via PM before dependent implementation. This can be a compact table embedded in the plan.
5. **Per-task review and test record:** peer findings, severity, owner, fix or explicit risk disposition, test command/environment/result, failures, rerun result, and limitations. It identifies the task diff or commit range, requirement revision, reviewer identity, host and model. Reviewers and QA own their respective entries.
6. **Final acceptance record:** product manager's criterion-by-criterion result, EL's technical result, QA's quality result, remaining risks, and PM's delivery report. Each names the frozen integrated candidate ID and requirement revision. Product acceptance states for each user-visible criterion what was exercised directly, the method and observed result; if direct exercise is impossible, PM records why and what QA evidence was relied on. For a goal job, judge verdict references this evidence. A board post points to durable artifacts; a 200-character board message is not itself the specification.

Use `DONE: <result and how to check>` for checkable claims and reply with `VERIFIED` or `FAILED` only from a real verifier. Ordinary peer review uses explicit review comments or a review record so the built-in verifier count is not misleading. Every requirement and defect has a stable ID and owner. Changes to a requirement keep the earlier text or diff and note who approved the revision. Every bounded role invocation gets a durable brief path; on Codex its first board post is `BRIEF: <path> tasks: <IDs>` so supervisor replacement can recover the task when the original spawn message is unavailable.

**Candidate identity.** Each implementation task has an immutable commit or diff against a named base; concurrent writers use separate worktrees or branches where supported, and otherwise serialize edits to shared files. The EL integrates reviewed tasks, resolves conflicts, and freezes one integrated source candidate before final QA. Its ID is a recorded SHA-256 manifest of sorted relative paths and file hashes for every deliverable code, test, skill Markdown, configuration, and requirement file, whether or not the project uses Git; Git commit IDs are recorded as provenance when available. At freeze, EL records the explicit deliverable path list, including immutable requirement baselines. All evidence-only review, test-result, traceability-result, acceptance, status, and evaluation files live outside that list; a file containing operative requirements, code, tests, or skill instructions cannot be excluded as evidence. If a planning artifact combines requirements and results, split the mutable result records out before freeze. Additions or removals of deliverable files update the path list and candidate ID. Recording evidence then leaves the candidate unchanged while changing a requirement baseline changes both its revision and candidate identity. A task review is reopened when a changed file intersects its reviewed diff or a linked PR/ER changes; EL and reviewer jointly record that assessment. Any change to the integrated source candidate refreshes all final QA, product, EL, and judge gates against the new candidate. Evidence-only edits to excluded record paths do not reopen those gates.

## Operating sequence and handoffs

1. **Intake and provisional sizing.** PM captures the original request, constraints, existing authorization, and target repository. PM provisionally labels the work tiny, moderate, or complex only to choose the first invocation. Product manager identifies consequential ambiguities. PM asks the user only for a decision unavailable from prior authorization; unaffected work continues.
2. **Product baseline.** Product manager drafts PRs and acceptance criteria, with competitor research where relevant and possible. PM compares the proposed baseline to the original user request, checks marked inferences and exclusions, and returns errors to the product manager. A product manager's blocking ambiguity must be routed to the user via PM. Unresolved items name the tasks they block. There is no automatic request for user signoff on the entire baseline.
3. **Technical design and staffing.** EL maps PRs to ERs, architecture and tasks, decides the final tier and requested engineer pool from independent work streams, integration risk and review load, and may upgrade an earlier tier. PM uses a declared host slot budget when available in session metadata or configuration, together with observed active invocations and Swarm caps. Unknown host capacity leads to conservative serial dispatch, never member probe spawns. PM schedules root spawns in waves and tells EL what capacity is available. EL repartitions work if needed; independent review remains.
4. **Implementation.** EL assigns distinct engineering tasks and file or component ownership through the board. PM schedules bounded implementation invocations. Engineers work in isolated worktrees or branches when available, otherwise serialize shared edits, run focused checks, and return a durable task diff or commit and evidence. EL integrates in dependency order and checks interfaces. A role invocation returns after its bounded deliverable; PM does not assume that return frees a host slot, and follows the host's supported lifecycle and actual spawn result. QA can write acceptance checks from the product baseline before code exists.
5. **Review and repair.** PM assigns a fresh reviewer context for every delivered change, including QA test code. On Codex, `fork_turns="none"` is required for review, QA, product acceptance, verifier, and judge spawns; the host dry run must confirm support. Reviewers receive requirement IDs, task diff or commit, and verification commands, then inspect actual code and tests. They record findings before using the author's explanation as proof. The author fixes findings or requests a risk decision, and the same reviewer may recheck the fix. Critical or high findings left unfixed require the user's explicit decision via PM with EL recommendation. Medium or low findings need EL disposition and reviewer concurrence. Any finding that changes user scope needs a user decision regardless of severity. The author never dispositions its own finding.
6. **QA and acceptance.** QA writes or extends tests for the affected behavior and executes the relevant categories: acceptance and integration for changed flows; end-to-end for affected user journeys; performance when performance is a requirement or credible risk. The product manager owns user-facing thresholds and EL owns technical thresholds at baseline, before QA runs; missing thresholds trigger a request rather than an invented pass. QA explains omitted categories, EL concurs, and PM reports omissions. A different engineer reviews QA-written test code; in tiny mode, if the reviewer also writes a test, the PM/EL or another independent engineer reviews that test. Product manager directly exercises each user-visible criterion on the frozen candidate and records method and result; any reliance on QA evidence is identified with a reason. EL checks ERs and architecture on that same candidate. QA and product rejection routes to the owning engineer, then through renewed review and affected tests. A changed PR creates a new baseline revision and reopens linked gates.
7. **Completion.** PM compares every PR and explicit user request with the delivered candidate, ensuring exclusions or deferrals have the user's decision, every ER is accepted, peer findings have valid dispositions, and final QA/product/EL results name the current candidate and requirement revision. A code or requirement revision invalidates affected task reviews as defined above, and every final gate. If the job has a judge, its verdict reason must include `candidate=<id> req=<rev>`; PM compares those values with the current candidate and baseline before deactivation, requesting a fresh verdict on mismatch. Swarm's built-in gate checks only the latest `met`, not candidate freshness. A `not_met` verdict returns the named gap to its owner and reopens affected signoffs. PM reports delivered scope, verification evidence, known limits, marked inferences that were not user-approved, and any authorization needed for a separate deployment or publication.

The product manager assesses whether the built behavior meets product criteria, subject to the user's authority over scope; the EL determines whether the implementation meets technical criteria; QA determines whether test evidence supports release confidence. These three results are separate. The PM cannot equate a passing test suite with product acceptance, and the judge independently assesses the job goal rather than rubber-stamping any role. A technical dispute belongs to the EL; a product-fit dispute belongs to the product manager; a scope dispute belongs to the user via PM. If the product manager and EL disagree about whether a change alters scope, PM asks the user before accepting it.

## Scheduling and host mechanics

The PM maintains a small dependency board: ready, in progress, review, QA, blocked, accepted. It records each task's owner, prerequisite, planned next check, and actual status. The PM explicitly joins the board under an orchestrator key, reads unread messages at the start of each turn and before each wave, and routes action requests returned by agents. Reports to the user name concrete completed work, next work, blockers, and changed estimates. Whenever the PM ends a turn while work remains but no agent is running, it records the reason with `swarm wait --on`; it resumes the job when that dependency clears. A short task needs no artificial reporting cadence.

Claude agents receive `[swarm job: <job>]` and `[swarm role: <role>]` in their prompts; child spawns additionally require `[swarm spawn: <reason>]`. Codex agents receive a `<role>__<task>` task name because spawn messages are encrypted to hooks; a child explains its spawn on the board. Examples include `project_manager__report`, `product_manager__spec`, `engineering_lead__plan`, `engineer__api`, `reviewer__api`, `qa__acceptance`, `verifier__check`, and `judge__final` (the last two use built-in restricted roles). The invoking agent activates the job; both hosts can attach to one job only if they share a board and each session is configured. The skill provides both host examples and chooses the current host's syntax.

The skill requires a Swarm source revision containing custom-role routing from commit `634aece`; an installed plugin label such as `0.1.0` alone does not prove that capability. PM preflights the installed runtime and host tools before planning role dispatch. After the first safe role invocation has made a tool call and posted its `BRIEF:` line, `swarm status --job <job> --all-agents` must show that agent with the custom role, including if it has already returned. Do not judge enrollment immediately after spawn or from the active-only `who` roster. If the completed check still shows the host agent type, PM stops role-dependent work, reports the installed-runtime mismatch, and points to the needed update without auto-installing. Research tools and network access are checked separately when needed. A unit test of the checkout is not evidence that the installed hook has changed.

Before each wave PM uses the declared concurrency limit when one is available in session metadata or configuration; otherwise PM dispatches conservatively and serially. It counts current active invocations and checks Swarm's separate per-agent, per-job, and depth limits. A host spawn failure is a capacity signal and the task is requeued. Member agents never probe capacity by spawning: admitted attempts can consume nonrefundable Swarm caps even if the host launch fails. Root spawns by PM are the default; nested helpers are rare and synchronous. Codex's `stop_quiet_minutes` governs when Swarm marks an agent completed; it does not determine when the Codex host frees a concurrency slot. PM may reuse a Codex agent with `followup_task` for a bounded task in the same role, but cannot change its role or make an author review, QA, or accept its own work. Any role transition needing independence gets a fresh agent. A returned role invocation does not imply host slot release; the PM checks the host's supported stop/close/resume behavior, then schedules from observed availability. No close API is assumed. A four-slot host might run PM + product + EL, then PM + two engineers, then PM + reviewer + QA, then PM + product + EL for final acceptance. The exact waves follow observed availability and role handoffs. Record whether the declared budget includes the root; if that is unknown, count it conservatively. Count a returned agent as occupying its slot until host evidence says otherwise. If a required fresh independent context remains unavailable and no supported lifecycle action can release one, report a capacity blocker and the needed route (such as an attached fresh session or another authorized host). Do not keep retrying without a changed capacity signal or silently reuse an author as its reviewer.

If an agent fails, disappears, or is replaced by Swarm supervision, PM first fences the old writer: use a supported host stop/close operation and confirm it stopped, or confirm a supervisor replacement has fenced it. A stale board status alone is insufficient. PM posts a claim transfer before reassigning files. If the old writer cannot be stopped or confirmed, PM keeps shared files blocked or gives the replacement an independent workspace; it does not create concurrent writers in one checkout. The replacement reads the durable brief, request, current artifacts, and last committed task state, then treats partial edits as unreviewed input. If the board is down, agents can continue isolated work with clear ownership, while PM avoids new shared claims, member spawns needing board admission, and acceptance decisions until queued posts are delivered and state is reconciled. Conflicts are resolved by the file owner with review. An unrecoverable blocker is reported with evidence and the exact decision needed; completion is not forced to hide it.

## Scope and completion tests for the future skill

The first version is an instruction skill with role brief and artifact templates, not a new Swarm board schema or autonomous scheduler. It uses existing CLI and host spawn APIs. It explains how to scale down for small changes, how the EL requests engineers and PM executes root spawns, and how QA and product acceptance remain independent even when roles run sequentially. The skill cannot enforce arbitrary custom-role authority, prevent all shared-board context leakage, prove host capacity, fence a writer without host or supervisor support, or bind a judge verdict to a candidate in Swarm storage. Those remain PM workflow checks and documented limitations. It avoids assuming every user request authorizes deployment, publication, or production data changes.

The future skill is ready on a host only after that host's installed revision passes a role-enrollment smoke check and an independent operator executes preregistered scenarios on isolated sample work. The scenarios must cover: capacity and spawn-cap denial with requeue, an engineer loss with a safe ownership transfer, a seeded defect found and resolved through peer review, QA rejection and reroute, product rejection of an unmet criterion, a changed PR or source candidate reopening signoffs and judge verdict, and a final report tracing every original user requirement to evidence. A separate reviewer grades board posts, artifacts, and gate state against expectations written before the run; a negative control must fail. A design walkthrough can find ambiguity but cannot prove behavior. Record pass, fail, or pending separately for Claude and Codex, including installed source revision and any host capability not measured. Do not describe a host as working while its dry run is pending. Existing unit tests cover parser and enforcement logic in the checkout; these dry runs cover installed runtime behavior and the skill's agent workflow.
